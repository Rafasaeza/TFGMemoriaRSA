This evaluation assesses the operational resilience, throughput stability, and resource consumption of the end-to-end telemetry streaming pipeline under continuous real-time load. The evaluation campaign is structured over a two-day testing methodology: an automated monitoring script runs in the background capturing container runtime statistics (\texttt{docker stats}) across all stack services throughout the entire night, and the captured traces are subsequently analyzed quantitatively the following morning.

The evaluation is structured into two consecutive phases:
\begin{enumerate}
    \item \textbf{Day 1 (Nov 9--10, 2026):} Baseline soak test, problem discovery, and pipeline hardening.
    \item \textbf{Day 2 (Nov 10--11, 2026):} Post-remediation soak validation.
\end{enumerate}

%======================================================================
\subsection{Day 1: Baseline Soak Test, Problem Discovery, and Hardening}
\label{subsec:eval_day1}

\paragraph{Objective.}
The objective of this first soak test is to detect potential memory leaks, identify streaming lags, and verify whether the end-to-end system is fit for continuous real-time streaming without freezes, operational stoppages, or queue backpressure.

\paragraph{Evaluation Findings.}
The baseline execution ran continuously for 14.30 hours (from 2026-11-09 18:31:02 UTC to 2026-11-10 08:48:49 UTC), recording $N = 1,641$ discrete \texttt{docker stats} metric snapshots sampled at 30-second intervals. Over this duration, all containerized services remained fully operational with zero crashes, restarts, or unhandled exceptions. Ingested data integrity was verified at the storage sinks: exactly 233,412 rows were persisted into QuestDB (\texttt{fleet\_features}) with uninterrupted timestamps, and the Apache Spark Structured Streaming engines maintained strict zero-lag real-time parity with Redpanda ($\text{avgOffsetsBehindLatest} = 0.0$, $\text{maxOffsetsBehindLatest} = 0$).

As reflected in the data, all core processing components behaved strictly as expected:
\begin{itemize}
    \item The native Rust simulator operated with a flat footprint ($\sim6$~MiB), demonstrating that strict ownership and compile-time memory management prevent leaks entirely.
    \item The Apache Spark Structured Streaming engines operated as stateless transformers; after initial JVM heap warming (2.9~GiB), G1GC garbage collection stabilized memory at 1.7~GiB and 1.3~GiB without unbounded window growth.
    \item Redpanda and QuestDB exhibited downward stabilization, releasing temporary startup buffers and settling into steady off-heap memory footprints.
\end{itemize}

However, \textbf{MinIO S3 object storage exhibited an anomalous behavior}: its resident memory grew monotonically from 400~MiB up to 2.07~GiB (+406\%), diverging sharply from all other services. \paragraph{Root Cause Analysis: Unbounded Metadata Growth.}
Detailed inspection of the MinIO object store revealed that the disk space consumption had reached 128~GiB, despite the actual persisted Parquet telemetry data totaling only 321~MB. The remaining 127.5~GiB (99.7\% of the entire bucket) consisted of over 61,000 Apache Iceberg metadata JSON files.

Because Apache Iceberg commits a new metadata file ($v_N\text{.metadata.json}$) with each streaming micro-batch, and by default appends the complete historical snapshot log to every new version file, the size of individual metadata files escalated progressively throughout the run:
\begin{itemize}
    \item Early version ($v_1$): 12~KB.
    \item Intermediate version ($v_{1000}$): 872~KB.
    \item Mid-test version ($v_{10000}$): 8.3~MB.
    \item End-of-night version ($v_{17650}$): 15.0~MB.
\end{itemize}

With micro-batches executing every 3 seconds, Spark was serializing and transmitting a 15~MB JSON file to MinIO every 3 seconds. This caused quadratic storage growth ($O(N^2)$), inflated Spark commit latency from 180~ms to 3--5~seconds, and forced the MinIO daemon to retain massive inode and bloom filter structures in RAM, causing the observed memory drift.

\paragraph{Remediation and Storage Optimization.}
To eliminate unbounded metadata accumulation at the engine level, two critical table properties were injected into the Iceberg DDL schemas for both Bronze and Silver tables:
\begin{enumerate}
    \item \texttt{'write.metadata.delete-after-commit.enabled' = 'true'}: Instructs Spark to automatically purge obsolete metadata files synchronously upon committing new snapshots.
    \item \texttt{'write.metadata.previous-versions-max' = '5'}: Restricts the retained metadata history to the 5 most recent version files, bounding metadata file size permanently.
\end{enumerate}

Combined with an administrative purge of historical orphan metadata files and clearance of internal MinIO trash, this configuration achieved a \textbf{99.9\% reduction} in storage and stabilized commit latency, as shown in Table~\ref{tab:pipeline_remediation}.

\paragraph{Conclusions of Day 1.}
As seen in the first day of the test, the system can seem real time prepared, but many factors as the metadata size were not taken into account; through this first test, the problem was solved.
