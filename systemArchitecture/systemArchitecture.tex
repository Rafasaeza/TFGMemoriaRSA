\section{Introduction}

In this chapter, we delve deeper into the system architecture design. As illustrated in Figure \ref{fig:e2e-architecture}, the proposed solution is structured into distinct, modular tiers, forming an End-to-End Streaming Architecture.

The system relies on the following core layers:
\begin{itemize}
\item \textbf{Source Systems Layer:} This tier acts as the primary origin of truth. For the scope of this study, it comprises a high-performance simulation environment that generates all necessary operational and physical telemetry variables for subsequent analytics. In a prospective industrial deployment, this layer can be seamlessly extended to incorporate physical, production-grade autonomous mobile robots.
\item \textbf{Broker MQTT Layer:} Serving as the initial edge gateway, this layer receives live telemetry payloads published directly by the source systems. While future iterations of the architecture might bypass this boundary—routing data directly through the central event streaming bus—deploying an independent MQTT broker establishes a robust and lightweight communication bridge tailored for IoT edge devices and complies with the requirements of the VDA5050 protocol.
\item \textbf{Event Streaming Layer:} Functioning as the central nervous system of the application, this layer acts as a distributed event bus. It decouples the data emitters from the compute engines, guaranteeing reliable, low-latency message buffering and high-throughput streaming across the pipeline.
\item \textbf{Stream \& Processing Layer:} Dedicated to continuous stream processing, this layer performs real-time computations and data transformation. It is architected to efficiently handle and process massive volumes of high-frequency data streams.
\item \textbf{Data Lakehouse Layer:} Operating as the persistence backbone, this layer stores the historical telemetry required for downstream machine learning analytics. By adopting a Data Lakehouse paradigm, the system combines cost-effective object storage with DBMS-like ACID transactions. Furthermore, it implements the \textit{Medallion Architecture} (Bronze, Silver, and Gold tiers), preserving raw immutable ingestion data to ensure full reprocessing flexibility over time.
\item \textbf{Machine Learning Layer:} This analytical module fulfills the primary objective of the research: real-time anomaly detection through advanced machine learning models consuming refined features from the data lakehouse.
\item \textbf{Observability Layer:} Once operational metrics and diagnostic outputs are consolidated in the Gold layer, this tier presents actionable insights to operators through comprehensive visualization dashboards, enabling real-time monitoring of system health and robot anomalies.
\end{itemize}

\section{General Architectural Decisions}

In addition to the component-specific design decisions presented in the following sections, several cross-cutting architectural principles were established to guide the development of the entire platform.

\subsection{Containerized Microservice Architecture}

The complete platform was designed following a containerized microservice approach. Each functional layer of the architecture is deployed as an independent Docker container, including the source systems, messaging infrastructure, stream processing services, data storage components, and machine learning modules.

This modular design provides several advantages. First, it promotes loose coupling between system components, allowing individual services to be developed, tested, and maintained independently. Second, it simplifies system scalability, since each component can be replicated or upgraded without affecting the rest of the platform. Finally, it increases the long-term maintainability of the solution, as individual modules may be replaced by alternative implementations provided that the communication interfaces remain unchanged. Consequently, the architecture is centered on well-defined interfaces rather than on specific software implementations, facilitating future evolution of the platform.

\subsection{Interface-Oriented Design}

To maximize interoperability and future extensibility, communication between architectural layers is performed through standardized interfaces and message formats. This design principle ensures that a component can be replaced without requiring major modifications in the remaining layers. For example, the simulated AGV fleet used during development could be replaced by a real fleet management system, while preserving the same MQTT and VDA 5050 communication contracts. As a result, the architecture remains independent of specific hardware vendors or software providers.

\subsection{Continuous Integration and Version Control}

The development process follows modern software engineering practices based on distributed version control and continuous integration principles. Git was adopted as the central version control system, enabling traceability of architectural decisions, source code modifications, configuration changes, and experimental results throughout the project lifecycle. In addition, the containerized nature of the platform facilitates the implementation of future Continuous Integration and Continuous Deployment (CI/CD) pipelines, allowing automatic validation, testing, and deployment of updated system components.

\subsection{Event-Driven Architecture} An event-driven architecture was adopted as the communication paradigm for the entire platform. Rather than relying on direct point-to-point interactions between services, all components communicate through an intermediate event streaming layer. This approach significantly reduces coupling between producers and consumers, allowing individual services to evolve independently without affecting other parts of the system. Additionally, new services can be integrated into the platform with minimal effort by subscribing to the existing event streams. The event streaming layer acts as the system's central source of truth, providing a unified and consistent mechanism for distributing telemetry, operational events, and analytical results across the architecture. This design improves scalability, extensibility, and maintainability while facilitating the integration of future data processing and monitoring capabilities.

\section{Source Systems Layer}
In designing the data ingestion pipeline, a preliminary study was conducted to determine the optimal source of truth for the system. At first, the possibility of utilizing a physical Autonomous Mobile Robot (AMR) in real time was evaluated. However, this approach was discarded for the training phase due to two primary constraints: first, only a single real unit was available, which is insufficient to represent a fleet-scale source system; second, the physical hardware lacked the specific internal telemetry sensors required for comprehensive anomaly detection analytics.

As a second approach, a search was conducted for publicly available industrial datasets containing multi-variable telemetry from AGVs and AMRs. While several sources were identified, none provided the precise combination of electrical, mechanical, and thermal variables necessary for the anomaly detection module.

Given the limitations of both physical deployments and existing public datasets, the decision was made to implement a high-performance simulation framework capable of emulating an entire fleet of AGVs deterministically. Since the chosen simulation environment, built upon the open-source repository \texttt{bekirbostanci/vda5050\_vehicle\_simulator} \cite{bostanciVda5050}, did not natively incorporate deep physical powertrain dynamics, it was adapted to model core electromechanical and thermal variables. To ensure seamless integration with downstream data consumers, the messages published by the simulated robots strictly adhere to the \textbf{VDA 5050} \cite{vda5050standard} interoperability standard, extended to include custom telemetry payloads.

\section{MQTT Broker Layer} 
The adoption of the VDA 5050 communication standard directly influenced the design of the messaging layer. Since VDA 5050 defines MQTT as the underlying communication protocol between fleet management systems and AGVs, the incorporation of an MQTT broker became a fundamental architectural requirement. 

The broker layer acts as an intermediary between telemetry producers and data consumers, enabling asynchronous communication and decoupling the different system components. This approach allows producers and consumers to evolve independently while maintaining interoperability through standardized message exchanges. 

Several MQTT broker implementations were evaluated during the architectural design phase. Eclipse Mosquitto was ultimately selected due to its maturity, open-source licensing model, low resource consumption, Docker compatibility, and widespread adoption within Industrial Internet of Things (IIoT) environments. 

Furthermore, the publish/subscribe communication model facilitates horizontal scalability and simplifies the integration of future services. New consumers can subscribe to existing telemetry streams without requiring modifications to the source systems, making the architecture more extensible and maintainable.

\section{Event Streaming Bus Layer}
\subsection{Kafka provider selection}
To establish an enterprise-grade backbone for telemetry ingestion, storage, and analytics, the architecture incorporates a distributed event streaming platform. While the MQTT layer excels at lightweight device-to-broker messaging, an append-only distributed log is essential to serve as the immutable single source of truth, handle high-throughput event replay, and decouple analytical consumers from edge producers.

During the architectural design phase, distributed streaming technologies were evaluated. Although Apache Kafka represents the industry benchmark, \textbf{Redpanda} was selected as the central event broker. Redpanda provides complete protocol-level compatibility with the Apache Kafka API, allowing ecosystem tools—such as Apache Spark Structured Streaming and Kafka Connect—to operate seamlessly without modification or proprietary client adapters.

The decision to adopt Redpanda instead of traditional Apache Kafka is justified by several architectural advantages:
\begin{itemize}
    \item \textbf{Native Performance and Predictable Latency:} Redpanda is engineered in C++ utilizing the Seastar asynchronous framework with a thread-per-core architecture. This eliminates the Java Virtual Machine (JVM) runtime overhead and avoids Stop-the-World Garbage Collection (GC) pauses.
    \item \textbf{Architectural Simplicity and Self-Contained Topology:} Unlike traditional Kafka deployments requiring dedicated Apache ZooKeeper clusters or resource-intensive KRaft JVM controllers, Redpanda implements native Raft\cite{raftgithub} consensus embedded directly within the broker binary. This significantly reduces operational complexity, container footprint, and deployment startup times.
    \item \textbf{Resource Efficiency in Edge and Development Environments:} The lightweight footprint of Redpanda enables high throughput and reliable partitioned persistence while conserving host computing resources, making it exceptionally well-suited for containerized edge gateways and Proof-of-Concept (PoC) deployments.
    \item \textbf{Integrated Developer Tooling:} The platform bundles the \texttt{rpk} management utility and the Redpanda Console user interface out of the box, streamlining topic inspection, consumer-group monitoring, and partition offset observability without requiring external monitoring containers.
\end{itemize}

By deploying Redpanda with four partitions per telemetry topic (\texttt{vda5050-state}) keyed by manufacturer and serial identifier (\texttt{manufacturer:serial}), the streaming tier guarantees strict per-asset chronological ordering while simultaneously unlocking parallel multi-threaded consumption for downstream real-time storage (QuestDB) and scalable distributed analytics (Apache Spark).

\section{Streaming Integration and Inter-Service Connectivity}
A critical requirement of the event-driven architecture is ensuring clean separation of concerns across the ingestion, streaming, storage, and processing tiers. Rather than tightly coupling producers and consumers to the central streaming bus, the integration topology relies on standardized connectors and specialized bridges. This approach isolates protocol adaptations to the respective system boundaries, preserving the raw VDA~5050 telemetry format within the central event log.

The rationale and implementation details for each integration interface are summarized below:

\subsection{MQTT to Event Streaming Ingestion Layer}
An architectural decision was required to establish the data bridge between the edge messaging layer (Eclipse Mosquitto) and the central event streaming bus (Redpanda), ensuring that vehicle telemetry producers remain decoupled from Kafka-specific protocols.

During the design phase, deploying a dedicated \textbf{Apache Kafka Connect MQTT Source connector} was evaluated to maintain a unified Kafka Connect framework across all integration points. However, this option was discarded due to the substantial resource overhead associated with hosting a separate Java Virtual Machine (JVM) runtime for simple protocol translation, which was deemed disproportionate for the edge ingestion stage.

Consequently, it was decided to adopt \textbf{Telegraf} as a lightweight, dedicated bridging agent. Written in Go, Telegraf provides native MQTT client and Kafka producer capabilities with a minimal memory and compute footprint, making it significantly more resource-efficient than a JVM-based connector. This decision achieves the required protocol bridging while conserving host resources and preserving the original, unmodified telemetry payload as it enters the event bus.

\subsection{Streaming to Time-Series Persistence: Decoupled Kafka Connect for QuestDB}
For real-time operational monitoring and visualization in Grafana, events must be streamed continuously into \textbf{QuestDB}. Instead of relying on bespoke consumers or embedding message-bus client logic into the storage layer, the industry-standard \textbf{Apache Kafka Connect} framework was adopted in sink mode (\texttt{io.questdb.kafka.QuestDBSinkConnector}).
\begin{itemize}
    \item \textbf{Fault Isolation:} Operating the sink inside a dedicated Kafka Connect container isolates ingestion buffering, offset commits, and deserialization errors from both the broker and the database engine.
    \item \textbf{Custom Single Message Transform (SMT):} Because columnar time-series databases like QuestDB enforce scalar relational types and reject heterogeneous nested object arrays, a custom Java SMT (\texttt{StringifyFields\$Value}) was developed. This transform executes in memory at the sink boundary, serializing the VDA~5050 \texttt{information} and \texttt{errors} arrays into plain JSON strings (\texttt{VARCHAR}). This enables downstream SQL querying via QuestDB's native \texttt{json\_extract()} functions without altering the canonical event stored in Redpanda.
    \item \textbf{Structural Flattening:} Standard Connect transformations (\texttt{Flatten\$Value}) map nested position and kinematics structures (e.g., \texttt{agvPosition.x}) directly into scalar database columns (\texttt{agvPosition\_x}).
\end{itemize}
\subsection{Event Streaming to Analytical Processing Connectivity}
An architectural evaluation was conducted to determine how to interface the central event streaming bus (Redpanda) with the analytical engine (\textbf{Apache Spark}) for downstream anomaly detection workloads.

Specifically, it was assessed whether an intermediate connector service or an external data-staging layer was required to bridge both systems. It was decided to connect Apache Spark directly to Redpanda by leveraging Spark's built-in, native Kafka streaming support. 

Because Apache Spark incorporates first-class Kafka protocol consumer capabilities out of the box, deploying a dedicated connector service or third-party middleware was deemed unnecessary. This decision significantly simplifies the deployment topology, reduces the overall component footprint, and eliminates architectural redundancy, allowing analytical workloads to consume raw telemetry streams directly from the message bus with minimal latency.

\section{Stream \& Processing Layer: Apache Spark}
\label{sec:spark-stream-processing}

In defining the computational backbone for telemetry transformation, analytical feature engineering, and scalable inference, an architectural decision was made regarding the stream processing engine. \textbf{Apache Spark}, utilizing its \textbf{Structured Streaming} framework, was selected as the central engine for this layer.

In accordance with the scope of this chapter, this section outlines the architectural design decisions, component responsibilities, and data contracts that govern the stream processing tier, whereas concrete job code, container configurations, and execution scripts are addressed in the implementation phase (Chapter~\ref{chap:system_implementation}).

While distributed event logs like Redpanda provide durable message buffering, they lack high-level compute primitives for complex multi-stage data processing and distributed machine learning inference. Apache Spark was selected based on the following architectural design principles:
\begin{itemize}
    \item \textbf{End-to-End Horizontal Scalability:} Telemetry volumes scale proportionally with the number of operational AGVs. Decoupling stream processing into a distributed engine ensures that computational bottlenecks are eliminated at the architectural level, allowing processing capacity to scale across partitions without altering application logic.
    \item \textbf{First-Class Lakehouse Integration:} Selecting an engine with native support for open table formats (\textbf{Apache Iceberg}) ensures transactional consistency (ACID guarantees), snapshot isolation, and seamless interoperability with the S3-compatible storage layer without requiring external data ingestion services.
    \item \textbf{Adoption of a Dual-Sink Streaming Pattern:} Rather than coupling stream processing to a single egress target, it was decided to adopt a dual-sink architectural pattern across processing stages. Under this design decision, Spark concurrently commits processed records to historical Iceberg tables for long-term analytics while republishing the transformed events back into dedicated Redpanda topics for low-latency downstream consumption.
\end{itemize}

From an architectural perspective, the trade-off between continuous, single-event streaming (as offered by engines such as Apache Flink or Kafka Streams) and the micro-batch execution model was evaluated. While single-event engines achieve marginally lower nominal latencies, the micro-batch approach was selected because the sub-second latency provided by Spark Structured Streaming fully satisfies the temporal requirements of AGV telemetry (sampling between 1~Hz and 10~Hz). Furthermore, micro-batching significantly simplifies transaction coordination, commit atomicity, and file compaction when interfacing with lakehouse table formats, offering a more balanced architectural trade-off for this platform.

\subsection{Medallion Processing Pipeline and Job Topology}

To avoid monolithic processing architectures and enforce strict separation of concerns across data maturity levels, the stream processing tier is decomposed into three decoupled streaming stages following the \textbf{Medallion Architecture} pattern (Bronze, Silver, and Gold tiers). Each stage is architecturally designed around distinct operational contracts, input/output interfaces, and analytical responsibilities:

\begin{enumerate}
    \item \textbf{Job 1: Raw to Bronze (State-Change Deduplication):}
    High-frequency AGV telemetry often emits redundant messages where physical states and operational variables remain unchanged between consecutive sampling intervals, with only the timestamp field updating. Ingesting these identical records directly into analytical storage introduces unnecessary storage bloat and skews downstream machine learning algorithms.

    To resolve this at the architectural boundary, the Bronze ingestion stage establishes a state-change filtering contract. Consuming from the raw \texttt{vda5050-state} topic, this job evaluates changes across physical variables and operational states (e.g., position coordinates, battery charge, motor temperature, driving mode) rather than relying solely on temporal increments. Only records representing genuine state transitions or physical measurements changes are persisted to the Bronze Iceberg tier, while concurrently republished to the intermediate topic \texttt{vda5050-state-deduplicated} to supply downstream consumers with high-density, noise-free state data.

    \item \textbf{Job 2: Bronze to Silver (Feature Extraction and Kinematic Aggregations):}
    The architectural role of the Silver stage is to isolate feature engineering from both raw ingestion and downstream inference. Consuming from \texttt{vda5050-state-deduplicated}, this stage unpacks nested telemetry structures and translates raw sensor readings into canonical, model-ready features (e.g., instantaneous electrical power, rolling-window speed differentials, and acceleration vectors). Following the dual-sink contract, the enriched feature set is materialized into the Silver Iceberg tier for offline model training and historical analysis, while simultaneously emitted to the \texttt{fleet-features} Redpanda topic for real-time downstream consumers.

    \item \textbf{Job 3: Silver to Gold (Distributed Real-Time Anomaly Inference):}
    To operationalize anomaly detection at scale, the architecture incorporates model inference directly within the distributed streaming topology rather than relying on an isolated single-process inference service. This design decision ensures that inference throughput scales horizontally alongside data partitions as the robot fleet expands. Consuming the structured feature stream from \texttt{fleet-features}, this stage applies pre-trained anomaly detection models across distributed partitions in real time. The resulting diagnostic predictions—comprising anomaly scores, classification flags, and reconstruction metrics—are committed to the Gold Iceberg tier for compliance and historical auditing, while concurrently published to the \texttt{ai-anomalies} topic for immediate ingestion into QuestDB and visualization in Grafana. The specific machine learning models, training procedures, and mathematical architectures are addressed separately in the Machine Learning Layer design.
\end{enumerate}
