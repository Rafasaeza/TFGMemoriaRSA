\chapter{System Architecture Design}
\label{chap:system_architecture}

\section{Introduction}

In this chapter, we delve deeper into the system architecture design.
As illustrated in Figure \ref{fig:e2e-architecture}, the proposed solution is structured into distinct, modular tiers, forming an End-to-End Streaming Architecture.

The system relies on the following core layers:
\begin{itemize}
    \item \textbf{Source Systems Layer:} This tier acts as the primary origin of truth.
    For the scope of this study, it comprises a high-performance simulation environment that generates all necessary operational and physical telemetry variables for subsequent analytics.
    In a prospective industrial deployment, this layer can be seamlessly extended to incorporate physical, production-grade autonomous mobile robots.

    \item \textbf{Broker MQTT Layer:} Serving as the initial edge gateway, this layer receives live telemetry payloads published directly by the source systems.
    While future iterations of the architecture might bypass this boundary—routing data directly through the central event streaming bus—deploying an independent MQTT broker establishes a robust and lightweight communication bridge tailored for IoT edge devices and complies with the requirements of the VDA5050 protocol.

    \item \textbf{Event Streaming Layer:} Functioning as the central nervous system of the application, this layer acts as a distributed event bus.
    It decouples the data emitters from the compute engines, guaranteeing reliable, low-latency message buffering and high-throughput streaming across the pipeline.

    \item \textbf{Stream \& Processing Layer:} Dedicated to continuous stream processing, this layer performs real-time computations and data transformation.
    It is architected to efficiently handle and process massive volumes of high-frequency data streams.

    \item \textbf{Data Lakehouse Layer:} Operating as the persistence backbone, this layer stores the historical telemetry required for downstream machine learning analytics.
    By adopting a Data Lakehouse paradigm, the system combines cost-effective object storage with DBMS-like ACID transactions.
    Furthermore, it implements the \textit{Medallion Architecture} (Bronze, Silver, and Gold tiers), preserving raw immutable ingestion data to ensure full reprocessing flexibility over time.

    \item \textbf{Machine Learning Layer:} This analytical module fulfills the primary objective of the research: real-time anomaly detection through advanced machine learning models consuming refined features from the data lakehouse.

    \item \textbf{Observability Layer:} Once operational metrics and diagnostic outputs are consolidated in the Gold layer, this tier presents actionable insights to operators through comprehensive visualization dashboards, enabling real-time monitoring of system health and robot anomalies.
\end{itemize}

These layers carry the telemetry. Section~\ref{sec:arch_utilities} describes a separate group of utilities added so that the simulated fleet can be exercised as a factory and so that the platform can be opened from one page. They support development and demonstration. They are not a stage of the pipeline.

\section{General Architectural Decisions}
\label{sec:arch_decisions}
\textit{Implementation: Chapter~\ref{chap:system_implementation}, Sections~\ref{sec:implementation_methodology} and~\ref{sec:containerized_deployment}.}

In addition to the component-specific design decisions presented in the following sections, several cross-cutting architectural principles were established to guide the development of the entire platform.

\subsection{Containerized Microservice Architecture}

The complete platform was designed following a containerized microservice approach.
Each functional layer of the architecture is deployed as an independent Docker container, including the source systems, messaging infrastructure, stream processing services, data storage components, and machine learning modules.

This modular design provides several advantages.
First, it promotes loose coupling between system components, allowing individual services to be developed, tested, and maintained independently.
Second, it simplifies system scalability, since each component can be replicated or upgraded without affecting the rest of the platform.
Finally, it increases the long-term maintainability of the solution, as individual modules may be replaced by alternative implementations provided that the communication interfaces remain unchanged.
Consequently, the architecture is centered on well-defined interfaces rather than on specific software implementations, facilitating future evolution of the platform.

\subsection{Interface-Oriented Design}

To maximize interoperability and future extensibility, communication between architectural layers is performed through standardized interfaces and message formats.
This design principle ensures that a component can be replaced without requiring major modifications in the remaining layers.
For example, the simulated AGV fleet used during development could be replaced by a real fleet management system, while preserving the same MQTT and VDA 5050 communication contracts.
As a result, the architecture remains independent of specific hardware vendors or software providers.

\subsection{Event-Driven Architecture}

An event-driven architecture was adopted as the communication paradigm for the entire platform.
Rather than relying on direct point-to-point interactions between services, all components communicate through an intermediate event streaming layer.
This approach significantly reduces coupling between producers and consumers, allowing individual services to evolve independently without affecting other parts of the system.
Additionally, new services can be integrated into the platform with minimal effort by subscribing to the existing event streams.
The event streaming layer acts as the system's central source of truth, providing a unified and consistent mechanism for distributing telemetry, operational events, and analytical results across the architecture.
This design improves scalability, extensibility, and maintainability while facilitating the integration of future data processing and monitoring capabilities.

\subsection{Separation of Training and Inference Pipelines}

The machine learning subsystem was designed following a clear separation between training and inference workloads.
Model training is performed offline using Python-based machine learning frameworks that consume historical data and engineered features stored in Apache Iceberg tables.
This approach provides flexibility for feature engineering, experimentation, hyperparameter tuning, and model evaluation.

In contrast, model inference is integrated directly into the Apache Spark streaming pipeline.
Once a model has been trained and validated, the promoted version is published through the model registry described in Section~\ref{sec:arch_ml} and loaded by the stream processing layer, so predictions are produced as new AGV telemetry events arrive.
This design avoids the latency associated with external prediction services and keeps inference on the same event bus as the rest of the platform.

The separation of training and inference responsibilities allows each workload to be optimized independently.
Training processes prioritize model accuracy and experimentation capabilities, whereas inference processes prioritize low latency, scalability, and operational reliability.
A newly trained model reaches the stream by promotion in the registry, without modifying the ingestion or feature pipelines.

\section{Source Systems Layer}
\label{sec:arch_source_systems}
\textit{Implementation: Chapter~\ref{chap:system_implementation}, Section~\ref{sec:source_system_simulation}.}

In designing the data ingestion pipeline, a preliminary study was conducted to determine the optimal source of truth for the system.
At first, the possibility of utilizing a physical Autonomous Mobile Robot (AMR) in real time was evaluated.
However, this approach was discarded for the training phase due to two primary constraints: first, only a single real unit was available, which is insufficient to represent a fleet-scale source system; second, the physical hardware lacked the specific internal telemetry sensors required for comprehensive anomaly detection analytics.

As a second approach, a search was conducted for publicly available industrial datasets containing multi-variable telemetry from AGVs and AMRs.
While several sources were identified, none provided the precise combination of electrical, mechanical, and thermal variables necessary for the anomaly detection module.

Given the limitations of both physical deployments and existing public datasets, the decision was made to implement a high-performance simulation framework capable of emulating an entire fleet of AGVs deterministically.
Since the chosen simulation environment, built upon the open-source repository \texttt{bekirbostanci/vda5050\_vehicle\_simulator} \cite{bostanciVda5050}, did not natively incorporate deep physical powertrain dynamics, it was adapted to model core electromechanical and thermal variables. The chassis is a differential drive: it does not sideslip, and the published yaw rate is a limited state rather than an instantaneous heading step. Section~\ref{sec:physical_modeling} states the motion law and the way it loads the motor.
To ensure seamless integration with downstream data consumers, the messages published by the simulated robots strictly adhere to the \textbf{VDA 5050} \cite{vda5050standard} interoperability standard, extended to include custom telemetry payloads.

The simulator can publish telemetry as soon as a vehicle is placed on the map. A training set gathered from isolated moves would still miss the operating context of a plant. Section~\ref{sec:arch_utilities} records how the fleet is driven as a factory, and which tools make that scenario runnable and visible.

\section{MQTT Broker Layer}
\label{sec:arch_mqtt}
\textit{Implementation: Chapter~\ref{chap:system_implementation}, Section~\ref{sec:mqtt_broker_implementation}.}

The adoption of the VDA 5050 communication standard directly influenced the design of the messaging layer.
Since VDA 5050 defines MQTT as the underlying communication protocol between fleet management systems and AGVs, the incorporation of an MQTT broker became a fundamental architectural requirement.

The broker layer acts as an intermediary between telemetry producers and data consumers, enabling asynchronous communication and decoupling the different system components.
This approach allows producers and consumers to evolve independently while maintaining interoperability through standardized message exchanges.

Several MQTT broker implementations were evaluated during the architectural design phase.
Eclipse Mosquitto was ultimately selected due to its maturity, open-source licensing model, low resource consumption, Docker compatibility, and widespread adoption within Industrial Internet of Things (IIoT) environments.

Furthermore, the publish/subscribe communication model facilitates horizontal scalability and simplifies the integration of future services.
New consumers can subscribe to existing telemetry streams without requiring modifications to the source systems, making the architecture more extensible and maintainable.

\section{Event Streaming Layer}
\label{sec:arch_event_streaming}
\textit{Implementation: Chapter~\ref{chap:system_implementation}, Section~\ref{sec:event_stream_implementation}.}

To establish an enterprise-grade backbone for telemetry ingestion, storage, and analytics, the architecture incorporates a distributed event streaming platform.
While the MQTT layer excels at lightweight device-to-broker messaging, an append-only distributed log is essential to serve as the immutable single source of truth, handle high-throughput event replay, and decouple analytical consumers from edge producers.

\subsection{Kafka provider selection}

During the architectural design phase, distributed streaming technologies were evaluated.
Although Apache Kafka represents the industry benchmark, \textbf{Redpanda} was selected as the central event broker.
Redpanda provides complete protocol-level compatibility with the Apache Kafka API, allowing ecosystem tools—such as Apache Spark Structured Streaming and Kafka Connect—to operate seamlessly without modification or proprietary client adapters.

The decision to adopt Redpanda instead of traditional Apache Kafka is justified by several architectural advantages:
\begin{itemize}
    \item \textbf{Native Performance and Predictable Latency:} Redpanda is engineered in C++ utilizing the Seastar asynchronous framework with a thread-per-core architecture.
    This eliminates the Java Virtual Machine (JVM) runtime overhead and avoids Stop-the-World Garbage Collection (GC) pauses.

    \item \textbf{Architectural Simplicity and Self-Contained Topology:} Unlike traditional Kafka deployments requiring dedicated Apache ZooKeeper clusters or resource-intensive KRaft JVM controllers, Redpanda implements native Raft\cite{raftgithub} consensus embedded directly within the broker binary.
    This significantly reduces operational complexity, container footprint, and deployment startup times.

    \item \textbf{Resource Efficiency in Edge and Development Environments:} The lightweight footprint of Redpanda enables high throughput and reliable partitioned persistence while conserving host computing resources, making it exceptionally well-suited for containerized edge gateways and Proof-of-Concept (PoC) deployments.

    \item \textbf{Integrated Developer Tooling:} The platform bundles the \texttt{rpk} management utility and the Redpanda Console user interface out of the box, streamlining topic inspection, consumer-group monitoring, and partition offset observability without requiring external monitoring containers.
\end{itemize}

By leveraging Redpanda as the event streaming backbone, the platform ensures durable event persistence, horizontal scalability, ordered event processing, and seamless integration with the wider Kafka ecosystem.
These characteristics make it an appropriate foundation for the real-time data ingestion and analytics requirements of the proposed architecture.

Topics were designed to provide clear separation of concerns, facilitate independent consumer processing, and support the event-driven communication model adopted throughout the platform.

A defining element of the topic design is the selection of a consistent partitioning key across the streaming backbone.
All telemetry topics use the composite key \texttt{manufacturer : serialNumber}, which in the VDA~5050 standard unambiguously identifies a single physical vehicle \cite{vda5050standard}.
This choice is motivated by two complementary architectural guarantees.
First, because a Kafka-compatible log preserves ordering only \emph{within} a partition, routing every message of a given AGV to a fixed partition ensures strict chronological ordering of its state transitions, a prerequisite for correct kinematic reconstruction and windowed feature computation downstream.
Second, prefixing the serial number with the manufacturer prevents hash collisions between distinct vehicles that could otherwise share an identical serial number.
At the same time, different vehicles are hashed to different partitions, allowing analytical consumers such as Apache Spark to process distinct AGVs in parallel.
The key is therefore applied uniformly across the ingestion, feature, and inference topics so that the per-asset ordering guarantee is preserved end to end across the Bronze, Silver, and Gold tiers.

\section{Streaming Integration and Inter-Service Connectivity}
\label{sec:arch_streaming_integration}
\textit{Implementation: Chapter~\ref{chap:system_implementation}, Section~\ref{sec:stream_integration_implementation}.}

A critical requirement of the event-driven architecture is ensuring clean separation of concerns across the ingestion, streaming, storage, and processing tiers.
Rather than tightly coupling producers and consumers to the central streaming bus, the integration topology relies on standardized connectors and specialized bridges.
This approach isolates protocol adaptations to the respective system boundaries, preserving the raw VDA~5050 telemetry format within the central event log, more details in the following subsections.

The end-to-end data pipeline and inter-service connectivity model are illustrated in Figure~\ref{fig:streaming-integration-architecture}.

The rationale and implementation details for each integration interface are summarized below:

\subsection{MQTT to Event Streaming Ingestion Layer}

An architectural decision was required to establish the data bridge between the edge messaging layer (Eclipse Mosquitto) and the central event streaming bus (Redpanda), ensuring that vehicle telemetry producers remain decoupled from Kafka-specific protocols.

During the design phase, deploying a dedicated Apache Kafka Connect MQTT Source connector was evaluated.
However, the MQTT ingestion boundary only requires protocol adaptation between MQTT and Kafka-compatible event streams, without the need for advanced connector lifecycle management, schema evolution, or stream transformations.
Consequently, introducing a full Kafka Connect framework at this stage was considered architecturally unnecessary.
Instead, Telegraf was selected as a dedicated telemetry ingestion agent because it provides native MQTT consumer and Kafka producer capabilities, enabling direct protocol bridging while preserving the original telemetry payloads.
This approach minimizes architectural complexity, reduces the number of operational dependencies, and keeps the ingestion boundary focused exclusively on message transport responsibilities.

\subsection{Streaming to Time-Series Persistence: Decoupled Kafka Connect for QuestDB}

For real-time operational monitoring and visualization in Grafana, events must be streamed continuously into \textbf{QuestDB}.
Instead of relying on bespoke consumers or embedding message-bus client logic into the storage layer, the industry-standard \textbf{Apache Kafka Connect} framework was adopted in sink mode (\texttt{io.questdb.kafka.QuestDBSinkConnector}).

The sink was first subscribed to \texttt{vda5050-state}. That topic carries the original VDA~5050 state message, a nested document of position, velocity, battery, and the information array that holds the motor telemetry. QuestDB stores a row of scalars. Turning the document into a row required transforms at the connector, and the table that resulted was a copy of the protocol. The dashboards and the model read the curated features and the anomaly scores, which are a different shape.

\textit{Architectural Decision: Sink the curated streams, not the raw state.}
The connector now follows the publications that those consumers already use. One sink reads \texttt{fleet-features}, the flat record produced by the Silver job, and appends it to the operational table of the same name. A second sink reads \texttt{ai-anomalies} and appends the scores. The tables are created before either connector starts, with a designated timestamp, a daily partition, and a retention of seven days. The connector appends into that schema. It does not invent a table from the first message. The anomaly record still contains one nested list, the per-channel contributions. That list is dropped at the connector, because the same channels are already carried as scalar fields. The Silver record needs no further transform.

\subsection{Event Streaming to Analytical Processing Connectivity}

An architectural evaluation was conducted to determine how to interface the central event streaming bus (Redpanda) with the analytical engine (\textbf{Apache Spark}) for downstream anomaly detection workloads.

Specifically, it was assessed whether an intermediate connector service or an external data-staging layer was required to bridge both systems.
It was decided to connect Apache Spark directly to Redpanda by leveraging Spark's built-in, native Kafka streaming support.

Because Apache Spark incorporates first-class Kafka protocol consumer capabilities out of the box, deploying a dedicated connector service or third-party middleware was deemed unnecessary.
This decision significantly simplifies the deployment topology, reduces the overall component footprint, and eliminates architectural redundancy, allowing analytical workloads to consume raw telemetry streams directly from the message bus with minimal latency.

\section{Stream \& Processing Layer: Apache Spark}
\label{sec:spark-stream-processing}
\textit{Implementation: Chapter~\ref{chap:system_implementation}, Section~\ref{sec:spark-implementation}.}

In defining the computational backbone for telemetry transformation, analytical feature engineering, and scalable inference, an architectural decision was made regarding the stream processing engine.
\textbf{Apache Spark}, utilizing its \textbf{Structured Streaming} framework, was selected as the central engine for this layer.

In accordance with the scope of this chapter, this section outlines the architectural design decisions, component responsibilities, and data contracts that govern the stream processing tier, whereas the implementation is addressed in (Chapter~\ref{chap:system_implementation}).

While distributed event logs like Redpanda provide durable message buffering, they lack high-level compute primitives for complex multi-stage data processing and distributed machine learning inference.
Apache Spark was selected based on the following architectural design principles:

\begin{itemize}
    \item \textbf{End-to-End Horizontal Scalability:} Telemetry volumes scale proportionally with the number of operational AGVs.
    Decoupling stream processing into a distributed engine ensures that computational bottlenecks are eliminated at the architectural level, allowing processing capacity to scale across partitions without altering application logic.

    \item \textbf{First-Class Lakehouse Integration:} Selecting an engine with native support for open table formats (\textbf{Apache Iceberg}) ensures transactional consistency (ACID guarantees), snapshot isolation, and seamless interoperability with the S3-compatible storage layer without requiring external data ingestion services.

    \item \textbf{Adoption of a Dual-Sink Streaming Pattern:} Rather than coupling stream processing to a single egress target, it was decided to adopt a dual-sink architectural pattern across processing stages.
    Under this design decision, Spark concurrently commits processed records to historical Iceberg tables for long-term analytics while republishing the transformed events back into dedicated Redpanda topics for low-latency downstream consumption.
\end{itemize}

From an architectural perspective, the trade-off between continuous, single-event streaming (as offered by engines such as Apache Flink or Kafka Streams) and the micro-batch execution model was evaluated.
While single-event engines achieve marginally lower nominal latencies, the micro-batch approach was selected because the sub-second latency provided by Spark Structured Streaming fully satisfies the temporal requirements of AGV telemetry (sampling between 1~Hz and 10~Hz).
Furthermore, micro-batching significantly simplifies transaction coordination, commit atomicity, and file compaction when interfacing with lakehouse table formats, offering a more balanced architectural trade-off for this platform.

\subsection{Medallion Processing Pipeline and Job Topology}

To avoid monolithic processing architectures and enforce strict separation of concerns across data maturity levels, the stream processing tier is decomposed into three decoupled streaming stages following the \textbf{Medallion Architecture} pattern (Bronze, Silver, and Gold tiers).
Each stage is architecturally designed around distinct operational contracts, input/output interfaces, and analytical responsibilities:

\begin{enumerate}
    \item \textbf{Job 1: VDA5050 State Writer (Raw to Bronze Persistence)} The telemetry generated by AGVs constitutes a continuous stream of operational data. While this stream is suitable for real-time communication between system components, it cannot be considered a reliable long-term source for analytics, auditing, or machine learning workloads. Messages stored only in Kafka are inherently transient and depend on retention policies, making them unsuitable as the primary source for historical analysis. Consequently, a persistent storage layer is required to preserve the complete history of vehicle telemetry. This historical repository enables offline data exploration, reproducible machine learning experiments, anomaly investigations, and system traceability. Several architectural alternatives were considered during the design phase. One possibility consisted of storing only the latest state of each AGV. This approach was discarded because anomaly detection models require access to historical behaviour patterns rather than individual snapshots. Another alternative involved applying state-change deduplication during ingestion to reduce storage requirements. However, due to the continuous variation of sensor readings and the stochastic noise introduced by the simulator, consecutive messages rarely contain identical payloads. The storage savings obtained from deduplication would therefore be limited while introducing additional processing complexity. For these reasons, the Bronze layer was designed as an immutable repository containing all incoming VDA5050 telemetry messages without modifications, filtering operations, or feature extraction. The \texttt{vda5050-state-writer} job is responsible for materialising this architectural decision by persisting the complete telemetry stream from the \texttt{vda5050-state} topic into an Apache Iceberg table. The resulting dataset serves as the authoritative historical record of the system. \item \textbf{Job 2: Bronze to Silver (Feature Extraction and Kinematic Aggregations)} Although the Bronze layer preserves the original telemetry stream, the VDA5050 message format is primarily designed for interoperability between fleet management systems and AGVs rather than analytical processing. As a consequence, messages contain nested structures and arrays that introduce unnecessary complexity for querying, statistical analysis, and machine learning workflows. To decouple the operational representation of telemetry from analytical requirements, a dedicated Silver layer was introduced. The objective of this layer is to expose a clean, structured, and domain-oriented representation of the information that can be consumed consistently by data analytics and machine learning components. The transformations performed in this stage are described below. \paragraph{Flattening} The first design decision concerns the representation of telemetry data. Directly exposing nested VDA5050 messages to downstream consumers would require every analytical component to repeatedly navigate hierarchical structures. Such an approach would increase implementation complexity and reduce interoperability between processing modules. To address this issue, a flattening process converts the original hierarchical message into a tabular schema. This representation is more suitable for Apache Spark processing, Apache Iceberg storage, and future machine learning pipelines while preserving the semantic meaning of the original telemetry data. \paragraph{Feature Selection} A second design objective consists of identifying which information is genuinely relevant for anomaly detection. The original VDA5050 messages contain numerous operational fields related to order execution, navigation state, and protocol management. However, the anomaly detection use case considered in this work focuses on identifying abnormal physical behaviour of AGVs through their telemetry measurements. For this reason, the selected features prioritise vehicle kinematics, battery indicators, motor telemetry, and safety-related signals while excluding protocol-oriented information that does not contribute to the detection of physical anomalies. The selected Silver-layer schema is composed of the following attributes: \begin{itemize} \item \texttt{timestamp}: Event timestamp used for temporal ordering and sequence reconstruction. \item \texttt{manufacturer}: AGV manufacturer identifier. \item \texttt{agv\_id}: Unique AGV identifier. \item \texttt{map\_id}: Identifier of the operational environment. \item \texttt{pos\_x}, \texttt{pos\_y}: Vehicle position coordinates. \item \texttt{vx}, \texttt{omega}: Forward speed and yaw rate. Lateral velocity is not a stored column. \item \texttt{driving}: Vehicle motion state. \item \texttt{battery\_charge}: Remaining battery charge level. \item \texttt{battery\_health}: Battery health indicator. \item \texttt{battery\_voltage}: Battery voltage measurement. \item \texttt{battery\_current}: Battery current measurement. \item \texttt{battery\_temperature}: Battery temperature measurement. \item \texttt{charging}: Battery charging state. \item \texttt{motor\_current}: Motor current consumption. \item \texttt{motor\_voltage}: Motor voltage measurement. \item \texttt{motor\_temperature}: Motor temperature measurement. \item \texttt{motor\_speed\_rad\_s}: Motor rotational speed. \item \texttt{motor\_torque\_nm}: Motor torque. \item \texttt{motor\_power\_w}: Motor power consumption. \item \texttt{back\_emf\_v}: Back electromotive force voltage. \item \texttt{fault\_active}: Active fault indicator. \end{itemize} The resulting Silver-layer schema establishes a common analytical representation of AGV telemetry data. This dataset serves as the foundation for subsequent machine learning processes, providing a consistent and domain-oriented view of the physical state of the vehicles while remaining independent of the original VDA5050 message structure.
    \item \textbf{Job 3: Real-Time Anomaly Inference.}
    The third stage consumes the curated stream published by the Silver job and publishes anomaly scores back onto the bus. The decisions that place this analysis on the live topic, rather than on a later scan of the lakehouse, are given in Section~\ref{subsec:arch_ml_inference}.
\end{enumerate}

\section{Data Lakehouse Layer: Storage Architecture}
\label{sec:data-lakehouse-layer}
\textit{Implementation: Chapter~\ref{chap:system_implementation}, Section~\ref{sec:data-lakehouse-implementation}.}

To establish the analytical persistence foundation of the platform, the architecture incorporates the \textbf{Data Lakehouse} paradigm.
While the event streaming bus (Redpanda) provides transient message buffering and the time-series engine (QuestDB) serves real-time dashboards, an immutable, cost-effective storage tier is required to persist the multi-tier Medallion datasets (Bronze, Silver, and Gold), store streaming execution checkpoints, and serve historical telemetry for offline machine learning model training.

\subsection{Object Storage Provider Selection: MinIO}
\label{subsec:minio-provider-selection}

In modern data architectures, decoupling compute from storage is a fundamental design principle.
Rather than deploying traditional distributed file systems (such as Apache HDFS) that introduce heavy operational overhead and tight coupling between compute nodes and physical disks, the architecture adopts \textbf{Object Storage} as the core persistence medium.

During the architectural evaluation of object storage engines for on-premise, edge, and containerized deployment, \textbf{MinIO} was selected based on the following architectural criteria:

\begin{itemize}
    \item \textbf{Industry-Standard S3 API Compatibility:} MinIO provides complete protocol-level compatibility with the Amazon S3 REST API.
    This native compatibility allows upstream compute engines—specifically Apache Spark via its \texttt{hadoop-aws} S3A connector—and modern table management engines (Apache Iceberg) to interface with the storage tier using standard S3 client libraries without requiring proprietary adapters.

    \item \textbf{Hybrid and Edge Deployment Portability:} In industrial cyber-physical environments, telemetry architectures frequently run on local edge infrastructure or on-premise factory servers before synchronizing with corporate data centers.
    MinIO enables a cloud-native S3 storage layer directly within containerized on-premise environments, ensuring that analytical pipelines can be migrated seamlessly to public cloud object stores (such as AWS S3 or Google Cloud Storage) simply by updating connection endpoints, without modifying data access logic.

    \item \textbf{High-Throughput Columnar and Micro-Batch Workloads:} Written in Go, MinIO delivers lightweight resource consumption and high sequential read/write throughput.
    These characteristics are critical for handling the concurrent demands of Apache Spark's streaming checkpoints and continuous Parquet file ingestion.

    \item \textbf{Strong Consistency for Lakehouse Table Formats:} Modern lakehouse table formats, such as Apache Iceberg, rely on atomic commit guarantees and strong read-after-write consistency to manage metadata snapshots and prevent race conditions during concurrent write operations.
    MinIO provides immediate consistency for all object operations out of the box, fulfilling this foundational requirement.
\end{itemize}

\subsection{Table Format Selection: Apache Iceberg}
\label{subsec:table-format-iceberg}

Object storage engines such as MinIO provide durable byte-level persistence, but relying directly on raw columnar files (for example, bare Apache Parquet) introduces significant limitations in a concurrent streaming environment.
In particular, raw files offer no transactional guarantees, suffer from the ``small files problem'' under continuous micro-batch appends, and can expose dirty or partial reads when an analytical query overlaps with an ongoing write.
To overcome these issues, modern Lakehouse architectures interpose an open \textbf{Table Format} layer between the object store and the compute engines, endowing the data lake with database-grade semantics \cite{apache_iceberg}.

The three leading open table formats---\textbf{Apache Hudi}, \textbf{Delta Lake}, and \textbf{Apache Iceberg}---were considered during the design phase.
\textbf{Apache Iceberg} was selected as the analytical table format of the platform on the basis of the following architectural drivers:

\begin{itemize}
    \item \textbf{Engine-Agnostic, Vendor-Neutral Specification:} Unlike Delta Lake, which has historically been closely associated with the Spark and Databricks ecosystem, Iceberg was designed from its inception as an open, engine-neutral specification.
    This enables the write path to rely on Spark Structured Streaming while leaving the read path free to use distributed SQL engines, DuckDB, or pure Python tooling (for example, \texttt{pyiceberg}) for offline machine learning, without runtime lock-in.

    \item \textbf{ACID Transactions and Snapshot Isolation:} Iceberg provides serializable isolation through an optimistic concurrency model built on atomic metadata commits.
    This guarantees that continuous micro-batch ingestion performed by Spark never interferes with the long-running, read-heavy scans issued by offline model-training routines, as readers always observe a consistent table snapshot.

    \item \textbf{Fit for Append-Only Telemetry Workloads:} While Apache Hudi is heavily optimized for Change Data Capture scenarios with frequent record-level updates and deletes, cyber-physical AGV telemetry is strictly append-only.
    Iceberg offers a leaner metadata layout better suited to high-throughput sequential appends and automated file compaction, without the record-indexing overhead that Hudi introduces.

    \item \textbf{Safe Schema Evolution:} As robotic platforms evolve, their telemetry payloads may add new diagnostic fields or retire obsolete ones.
    Iceberg supports column addition, renaming, and reordering as a purely metadata-level operation, preserving backward compatibility without rewriting historical Parquet files.
\end{itemize}

\subsection{Automated Lakehouse Maintenance Architecture}
\label{subsec:arch-lakehouse-maintenance}
\textit{Implementation: Chapter~\ref{chap:system_implementation}, Section~\ref{subsec:lakehouse-maintenance-job}.}

While low-latency micro-batching (15~seconds for Bronze and 3~seconds for Silver) fulfills the near-real-time ingestion requirements of the platform, it inherently introduces the \textit{small files problem} as an architectural side effect. Over continuous 24/7 industrial operation, appending new Parquet data files every few seconds produces tens of thousands of fragmented objects and inflates the commit snapshot tree within object storage. Left unmitigated, this file fragmentation severely degrades the metadata listing speed, partition pruning efficiency, and sequential scanning throughput of downstream machine learning training workflows.

To prevent performance degradation without burdening the real-time ingestion path, the architecture incorporates an independent, decoupled \textbf{Lakehouse Maintenance Tier}. Rather than performing inline compaction during micro-batch execution---which would destabilize streaming latencies---maintenance is orchestrated as an auxiliary operational component operating outside the main Medallion data flow. Architecturally, the maintenance tier addresses three distinct optimization concerns:
\begin{enumerate}
    \item \textbf{Data File Compaction:} Merging thousands of small micro-batch Parquet files into standardized target-sized columnar blocks (64~MiB) to optimize sequential I/O and columnar compression ratios.
    \item \textbf{Manifest Optimization:} Re-indexing and defragmenting Iceberg manifest files and manifest lists to accelerate file pruning during query planning.
    \item \textbf{Snapshot and Metadata Expiration:} Purging historical snapshot metadata and unreferenced orphaned Parquet data files that have been superseded by compacted files, bounding storage growth and metadata parsing overhead.
\end{enumerate}
Crucially, the maintenance process is triggered on demand through automated metadata inspection rather than arbitrary execution schedules, optimizing compute resource utilization in resource-constrained edge deployments.

\subsection{Bifurcated Storage Architecture: Operational vs. Analytical Persistence}
\label{subsec:bifurcated-storage}

A core architectural decision of the proposed platform is the explicit decoupling between the \textbf{operational time-series store} (QuestDB) and the \textbf{analytical object store} (MinIO):

\begin{itemize}
    \item \textbf{Operational Path (QuestDB):} Optimized for low-latency ingest and high-frequency SQL aggregation across rolling time windows, dedicated to live operator visualization in Grafana.
    \item \textbf{Analytical Path (MinIO / Lakehouse):} Optimized for massive, append-only historical telemetry persistence in columnar Parquet format, multi-tier Medallion curation, and high-throughput batch scanning required for offline machine learning model training.
\end{itemize}

This bifurcated storage design isolates analytical queries and heavy machine learning workloads from live operational monitoring, ensuring that intensive model training scans do not degrade dashboard rendering performance or message ingestion throughput.

\section{Machine Learning Layer}
\label{sec:arch_ml}
\textit{Implementation: Chapter~\ref{chap:system_implementation}, Section~\ref{sec:ml_pipeline_implementation}.}

The Machine Learning (ML) layer is the analytical tier that detects electromechanical and thermal anomalies in the AGV telemetry. Offline model development and online scoring have different lifecycles, latency budgets, and failure modes, so the layer is split into two operational perspectives and bound by two interfaces: a shared preprocessing contract and a model-registry control plane.

\begin{enumerate}
    \item \textbf{Training perspective.} An independent containerized service reads historical telemetry from the Silver lakehouse, builds the windows defined by the shared contract, standardizes them, and trains and selects the reconstruction model. It stays off the operational streaming path.
    \item \textbf{Inference perspective.} Scoring runs inside the Apache Spark Structured Streaming job that consumes the platform event bus. Placing the forward pass in that job avoids a remote prediction service and the network hop, serialization boundary, and availability coupling that a REST or gRPC model server would add.
\end{enumerate}

The two perspectives stay aligned only if a live record is prepared in the same way as a training record, and if both sides use the model currently in force. The preparation contract is decided with the real-time inference path (Section~\ref{subsec:arch_ml_inference}). The model in force is the production version in MLflow (Section~\ref{subsec:arch_ml_model}). Figure~\ref{fig:ml-subsystem-architecture} shows both interfaces.

\subsection{Data Preparation and Shared Preprocessing Pipeline}
\label{subsec:arch_ml_prep}

The training service reads the Silver table \texttt{fleet\_features}. Iceberg snapshot isolation supplies a stable table version for that read, so a long training scan does not lock the streaming commits that continue to append telemetry.

Preparation follows the order required to keep the fitted baseline honest:
\begin{enumerate}
    \item \textbf{Projection onto the detection subspace.} Training retains the channels the model may see, in a fixed order: planar and angular velocity, battery voltage, current and temperature, and motor current, temperature and power. Records outside that subspace are discarded. The remainder are ordered by vehicle and by event time. The same list is what inference must apply; the reason it is held in a shared contract is given in Section~\ref{subsec:arch_ml_inference}.
    \item \textbf{Per-vehicle windows, then a chronological split.} Sliding windows are built independently for each vehicle. A window never mixes two vehicles, and a window that contains a temporal gap is not emitted. Within each vehicle, earlier windows form the training split and later windows the validation split, so fitting cannot observe that vehicle's future operation.
    \item \textbf{Standardization fitted on the training windows only.} Mean and variance are estimated on the training windows. Validation windows are transformed with those frozen parameters and do not participate in the estimate. The tensors that enter the model have shape $\mathbf{X} \in \mathbb{R}^{B \times W \times F}$, where $B$ is the batch size, $W$ the window length fixed by the contract, and $F$ the number of contracted channels.
\end{enumerate}

\paragraph{Feature scaling.}
The contracted channels do not share a physical unit. Motor and battery temperatures move over tens of degrees, while velocities and currents occupy a much smaller numeric range. Fed to a squared reconstruction loss, the large-magnitude channels would dominate the gradient and the anomaly score, and a genuine deviation in a small-magnitude channel would barely move either. Standardization (zero mean and unit variance per channel) places every contracted signal on a common numeric footing.

Robust range scaling was set aside. The detector is trained on the normal operating regime, and the mean and variance of that regime are the baseline that inference must reuse. A quantile scaler would describe a different baseline and would still have to be frozen and shipped with the model; it was not the selected transform.

\subsection{Model Architecture and Training Decisions}
\label{subsec:arch_ml_model}

The standardized windows are the input of the training loop. Model selection is governed by the following decisions:

\begin{itemize}
    \item \textbf{Gated Recurrent Unit (GRU) Topology:}
    Industrial AGV telemetry exhibits continuous temporal dependencies. In accordance with the state of the art analysis (Chapter~\ref{chap:state_of_the_art}, Section~\ref{sec:anomaly-taxonomy}), the \textbf{Gated Recurrent Unit Autoencoder (GRU-AE)} was selected as the foundational model architecture. Compared to traditional RNNs, GRUs mitigate vanishing and exploding gradients through internal gating. Compared to Long Short-Term Memory (LSTM) networks, GRUs use fewer gating equations and parameters, with corresponding gains in training time and in the cost of in-stream scoring \cite{dey2017gate}. The selected topology encodes the window, compresses it to a latent state, and decodes a reconstruction of the same length and width as the input.

    \item \textbf{Loss Criterion: Mean Squared Error:}
    The autoencoder is trained unsupervised to reconstruct normal operational sequences, minimizing the error between the input window $\mathbf{X}$ and its reconstruction $\hat{\mathbf{X}}$. Mean squared error was selected for two reasons:
    \begin{enumerate}
        \item \textit{Quadratic penalty on large residuals.} Squaring the residual emphasizes sharp electromechanical deviations over small sensor noise.
        \item \textit{Channel attribution.} The loss separates across channels:
        \begin{equation}
            \text{MSE}_j = \frac{1}{W} \sum_{t=1}^{W} \left( x_{t,j} - \hat{x}_{t,j} \right)^2
        \end{equation}
        The inference stage can therefore emit a scalar score and, when that score is elevated, the contribution of each contracted channel. That contribution is the diagnostic payload of the observability dashboards.
    \end{enumerate}

    \item \textbf{Optimization Algorithm: Adam:}
    \textbf{Adam} (Adaptive Moment Estimation) was selected as the optimizer. Per-parameter adaptive rates and momentum keep the updates stable on noisy robotic channels without a hand-tuned learning-rate schedule for each weight.

    \textit{Open comparison.} AdamW, SGD with Nesterov momentum, and RMSprop remain credible alternatives. Adam is the baseline of this design. An empirical comparison of convergence and generalization is left to the evaluation, and is not required to fix the data-flow architecture.

    \item \textbf{Plateau Learning-Rate Schedule:}
    The learning rate stays at its initial value while validation loss is still decreasing, and is reduced when that loss stops improving. The schedule adapts to the run. It does not impose a fixed decay timetable chosen before training.

    \item \textbf{Early Stopping on Validation Loss:}
    An unsupervised reconstructor overfits when it starts to reproduce the particular noise of the training windows, including behavior that should have remained surprising. Validation loss is monitored at each epoch. If it fails to improve over a patience interval, training stops and the parameters with the lowest validation loss are the ones retained for promotion.
\end{itemize}

\textit{Architectural Decision: MLflow as the Experiment Record and Model Repository.}
Once training runs were executed, registering each experiment by hand proved laborious. A trial is defined by the data interval, the window, the latent size, and the learning rate, and two trials can be compared only when those choices, the validation curve, and the retained weights stay attached to the run that produced them. A review of current practice for the machine learning lifecycle identified MLflow as the standard mechanism for that record, and it was adopted as the best fit for this platform~\cite{mlflow}.

The same adoption closes a second gap. Without a common repository, the streaming job has no agreed place from which to take the model currently in force: a directory of checkpoints does not say which run is the latest one that should be served. The MLflow Model Registry is that repository. Each run publishes the fitted scaler together with the selected weights, and the network is registered as a version. Inference resolves the version marked for production and loads the scaler published with that same run, so live windows are standardized with the mean and variance of the training split. A later model reaches the stream by promotion, and the streaming topology stays unchanged. The names under which those runs are stored, and the metric keys they share, are fixed in Section~\ref{subsec:arch_mlflow_record}.

\subsection{A Common Record for Every Training Run}
\label{subsec:arch_mlflow_record}

Storing a run is not the same as being able to compare it. After the first captures, each one was filed under its own experiment name, and each run logged the loss, the percentiles, and the scenario scores under keys chosen for that trial. MLflow places two runs in one table only when the keys are the same. A key that belongs to a single run never becomes a column, so the number cannot be sorted against the rest.

\textit{Architectural Decision: One experiment, one registry name, and one metric vocabulary.}
The runs that compete for promotion share a single experiment, \texttt{agv-anomaly-detection}, and a single registered model, \texttt{agv-gru-autoencoder}, the name already fixed by the model contract. A study that is not a candidate for the stream, such as a check of the simulator physics, uses another experiment, so its keys stay out of the promotion table. The run name states the configuration and the capture. The tracking server already records the start time, so the clock is left out of the name. The pattern is \texttt{gru-h}$\langle$hidden$\rangle$\texttt{-l}$\langle$latent$\rangle$\texttt{-w}$\langle$window$\rangle$\texttt{-}$\langle$dataset$\rangle$, for example \texttt{gru-h64-l32-w60-factory-2026-11-20}. The dataset token identifies the capture. A repetition of the same configuration keeps the same name and is distinguished by its start time and its run identifier.

A value chosen before the fit is a parameter. A value measured by the fit is a metric. The parameters, written once and under fixed keys, are the data interval, the feature list in contract order, the window size, the step, the maximum gap, the split ratio, the hidden size, the latent size, the number of layers, the dropout, the optimiser, the learning rate, the weight decay, the batch size, and the epoch cap. Window counts, losses, and score distributions are metrics, because they depend on the interval and on early stopping.

Every candidate run logs the same metric keys. A scenario that was not evaluated is an empty cell.
\begin{itemize}
    \item \textbf{Epoch curves,} one point per epoch: \texttt{train/loss}, \texttt{val/loss}, and \texttt{train/learning\_rate}.
    \item \textbf{The summary used to rank the run.} \texttt{val/loss\_best} is the sort key. With it go \texttt{train/epoch\_best}, \texttt{train/epoch\_stopped}, \texttt{train/duration\_s}, \texttt{data/windows\_train}, \texttt{data/windows\_val}, \texttt{val/score\_mean}, \texttt{val/score\_std}, and the validation percentiles \texttt{val/score\_p50}, \texttt{val/score\_p95}, and \texttt{val/score\_p99}. The mean and the standard deviation are the figures the metadata ships as the threshold baseline.
    \item \textbf{Channel attribution} on the validation windows. Each contracted channel logs its mean squared error as \texttt{val/feat\_mse/} followed by the channel name, and its share of the total as \texttt{val/feat\_share/} followed by the same name. The channel token is the name in the contract.
    \item \textbf{Scenario scores,} and only for a closed list of modes. Nominal operation uses \texttt{nominal\_drive}, \texttt{nominal\_loaded}, \texttt{nominal\_idle}, and \texttt{nominal\_charge}. Faults use the simulator fault names: \texttt{mechanical\_stall}, \texttt{gearbox\_degradation}, \texttt{wheel\_wear}, \texttt{bearing\_degradation}, \texttt{stator\_short\_circuit}, and \texttt{battery\_soh\_degradation}. Each scenario that is present logs \texttt{scenario/}$\langle$name$\rangle$\texttt{/mse} and \texttt{scenario/}$\langle$name$\rangle$\texttt{/windows}. The channel that dominates the scenario is recorded in the evaluation artifact. A metric has to be numeric, so that name is not given a metric key of its own.
\end{itemize}

Tags stay few and stable: \texttt{task} is \texttt{anomaly\_detection}, and the run also carries \texttt{model\_family}, \texttt{dataset\_id}, and \texttt{contract\_version}. They filter the table. They do not repeat the parameter list. Artifacts keep fixed paths: the scaler under \texttt{preprocessor/}, the training metadata under \texttt{metadata/}, the weights under \texttt{weights/}, the plots under \texttt{diagnostics/}, and the scenario report under \texttt{evaluations/}. Promotion continues to read the scaler and the metadata from the run of the production version. Runs already stored under earlier keys are left as they are. The vocabulary applies to every run recorded after this decision.

\subsection{Online Inference on the Live Stream}
\label{subsec:arch_ml_inference}

The platform has to analyze the fleet while it is operating. A score that appears only after a later scan of the lakehouse describes telemetry the operator has already stopped watching. The analysis is therefore applied to the live stream of curated features, which is the Redpanda topic \texttt{fleet-features}.

\textit{Architectural Decision: Score the live stream with the production model.}
Apache Spark Structured Streaming is the engine already subscribed to that bus, and it is the component that can take the model currently marked for production and apply it to \texttt{fleet-features} as micro-batches arrive. Scoring on a schedule against the Silver table was set aside for this path: that read would measure anomalies on data already stored, which is the historical path used to train the next model, not the real-time path. A remote prediction service had already been rejected because it would add a network hop between the stream and the score. Changing the model under analysis is a promotion in the registry. The streaming job resolves the production version and adopts a successor without a change to the topic or to the Bronze and Silver pipelines.

\textit{Architectural Decision: Shared Preprocessing Contract.}
The functions that turn a telemetry record into a model input were planned on the training side: which channels are kept and in which order, how a window is cut for one vehicle, and when a temporal gap makes that window unusable. Real-time scoring has to apply those same functions to \texttt{fleet-features}. Otherwise the production model reconstructs an input it was not trained on. Copying the functions into the streaming job would leave two definitions of the same rule, and the first change to a window or a channel would separate them. Those functions were therefore placed in one library, \texttt{ml-common}, which is the contract both sides follow. The contract fixes the feature list and its order, the window geometry, the maximum admissible gap between samples, the identity of the registered model, and the threshold policy. It carries no fitted statistics. The mean and variance of a given run travel with the production model, as decided in Section~\ref{subsec:arch_ml_model}.

Figure~\ref{fig:spark-streaming-pipeline} shows where this stage sits between a write and a publication. The Silver job writes \texttt{fleet\_features} to Iceberg and publishes the same curated records to the \texttt{fleet-features} topic. Inference does not read the table that was just written. It consumes the publication, because that is the real-time stream. The same scored batch is appended to \texttt{lakehouse.gold.ai\_anomalies} and published to the \texttt{ai-anomalies} topic drawn in the figure. QuestDB ingests that topic for the dashboards and retains it for seven days. The Gold table keeps the rows, so a count of classes in one year can be set beside the count in another. Maintenance compacts the table with Bronze and Silver and retains the last two snapshots, which means the comparison is a query on the current table. The Silver table remains the history from which a later model is trained.

What that publication carries is the output contract of the decision: the reconstruction score, the class assigned against the warning and anomaly levels of the production version (normal, suspicious, or anomalous), and, when the score is elevated, the channels that dominate the error.

\section{Observability Layer: Grafana Dashboards}
\label{sec:arch_observability}
\textit{Implementation: Chapter~\ref{chap:system_implementation}, Section~\ref{sec:grafana_implementation}.}

The operator has to see the fleet while it is moving, and the score of the model on the same clock. QuestDB already holds those series, as decided in Section~\ref{subsec:bifurcated-storage}. A dashboard that issues SQL against that store was preferred to a second consumer of the bus: the panel is a query, and the streaming path is left unchanged when a chart is added or removed.

Grafana is that surface. It connects to QuestDB with a read-only account, so a dashboard can select and cannot write. The boards are provisioned with the stack and refresh every few seconds. Five of them cover the prototype. Fleet Battery and Fleet Velocity follow the charge, the health, the electrical battery channels, and the linear and angular velocity of each vehicle. Fleet Powertrain Physics plots the motor and battery relations already computed by the simulator, so a fault that moves current, torque, or temperature is visible as a physical trace and not only as a score. Fleet Features shows the full Silver row, which is the table the model is trained on. AGV Anomaly Detection \& ML Inference shows the reconstruction error against the warning and anomaly levels of the production model, the class of each window, and the channels that dominate the error.

A vehicle filter on the boards limits the traces to one serial. The page is the operational view of the pipeline. It does not score, store, or command a vehicle. How an operator opens each board is described in Appendix~\ref{app:user_manual}.

\section{Supporting Utilities}
\label{sec:arch_utilities}
\textit{Implementation: Chapter~\ref{chap:system_implementation}, Section~\ref{sec:utilities_implementation}.}

The pipeline is sufficient to carry a message from a vehicle to a score. During development it became clear that it does not, by itself, make a factory scenario easy to run or easy to understand. There is no access to a real plant, and the records used to train the model have to come from a process that is as close as a simulation can get to one: vehicles that carry parts, wait, charge, and repeat, for long enough that the baseline is a working factory rather than a script of unrelated moves. Three tools were added for that reason. They simplify the tests and they make the use case visible. The signals the model learns remain those published by the simulator.

\subsection{Factory Orchestration with Node-RED}
\label{subsec:arch_factory_orchestrator}

The simulator accepts the orders a fleet controller would send. The first plan was to issue those orders directly, one mission after another, until the vehicles reproduced a small factory. Parts leave a production point, cross a warehouse, reach an assembly cell, and depart as a finished good, and each vehicle returns to charge when its battery requires it. That cycle is the context the training set has to contain. A model that has only seen a vehicle driving an empty route will treat an ordinary loaded trip, a pick, or a charge as a deviation.

Putting the sequence into practice showed how laborious the plan was. Each test had to place every vehicle, release the next order only when the previous one had finished, watch the batteries, and then repeat the cycle for as long as a training capture needs. A fault trial meant repeating it under the same timing. The procedure was understandable, and it could not supply the hours of coherent operation the dataset requires.

Node-RED was adopted as the master control of that factory. Stock, the role of each vehicle, the decision to dispatch a mission, and the decision to send a vehicle to charge are expressed as flows. The flows speak VDA~5050 orders and instant actions to the simulator, which is the same contract a real fleet controller would use, so the vehicles do not have a second, private interface for the simulation. Current, temperature, and battery state stay with the simulator. The orchestrator decides what the vehicle should do next, and the physics already modelled in the source system produce the telemetry. A fault is applied to the vehicle through that same control channel, which leaves the factory logic unchanged between a healthy capture and a faulty one. Extending a test is then a change in the flows, or a fault selected for one vehicle, rather than a new manual script.

\subsection{Digital Twin of the Factory}
\label{subsec:arch_digital_twin}

Once the factory ran unattended, a different difficulty remained. The Node-RED flows are explicit: a reader can follow which message is sent when a stock level or a battery crosses a threshold. Following that graph still leaves the plant itself hard to picture. It does not show where a vehicle is, which aisle it is crossing, or whether a warehouse is filling. Without a real shop floor to walk, that picture is part of judging whether the training data correspond to the intended use case. It is also part of checking a test. A mission that never completes, or a vehicle that never reaches its charger, is obvious on a layout and easy to miss in a log of orders.

The digital twin was added as a visualization of the factory the orchestrator already runs. It is an observer. Poses, missions, and connection state are reconstructed from the VDA~5050 messages on the broker, and the view can also draw the stock and production events the orchestrator publishes for its own supervision. The twin only subscribes. Vehicle commands and factory rules remain in Node-RED, so a change in the process appears in the twin because the messages change, and there is no second copy of the logic to keep aligned. The twin is a way to look at the automation during a test and during a demonstration. It contributes no sample to the training set, and it does not replace the simulator.

\subsection{Platform Entry Point}
\label{subsec:arch_platform_portal}

By the time the factory and the twin were in place, opening the system meant a broker, the streaming stack, the lakehouse, the time-series store, the dashboards, the model registry, the orchestrator, and the twin. Each service has its own interface. Starting a session meant recalling which address opened which tool, and a service that had failed to come up was noticed only when a later step had nothing to read.

A single entry point was placed in front of the platform. One page lists the services, links to each interface, and reports whether the service answers. From that page a test or a demonstration can reach any part of the system without a separate map of addresses. The page is a convenience for development and for showing the platform. The path from the vehicle to the anomaly score does not pass through it, and the pipeline runs whether or not the page is open.
