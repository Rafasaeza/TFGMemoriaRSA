\chapter{System Architecture Design}

\section{Introduction}

In this chapter, we delve deeper into the system architecture design.
As illustrated in Figure \ref{fig:e2e-architecture}, the proposed solution is structured into distinct, modular tiers, forming an End-to-End Streaming Architecture.

The system relies on the following core layers:
\begin{itemize}
    \item \textbf{Source Systems Layer:} This tier acts as the primary origin of truth.
    For the scope of this study, it comprises a high-performance simulation environment that generates all necessary operational and physical telemetry variables for subsequent analytics.
    In a prospective industrial deployment, this layer can be seamlessly extended to incorporate physical, production-grade autonomous mobile robots.

    \item \textbf{Broker MQTT Layer:} Serving as the initial edge gateway, this layer receives live telemetry payloads published directly by the source systems.
    While future iterations of the architecture might bypass this boundary—routing data directly through the central event streaming bus—deploying an independent MQTT broker establishes a robust and lightweight communication bridge tailored for IoT edge devices and complies with the requirements of the VDA5050 protocol.

    \item \textbf{Event Streaming Layer:} Functioning as the central nervous system of the application, this layer acts as a distributed event bus.
    It decouples the data emitters from the compute engines, guaranteeing reliable, low-latency message buffering and high-throughput streaming across the pipeline.

    \item \textbf{Stream \& Processing Layer:} Dedicated to continuous stream processing, this layer performs real-time computations and data transformation.
    It is architected to efficiently handle and process massive volumes of high-frequency data streams.

    \item \textbf{Data Lakehouse Layer:} Operating as the persistence backbone, this layer stores the historical telemetry required for downstream machine learning analytics.
    By adopting a Data Lakehouse paradigm, the system combines cost-effective object storage with DBMS-like ACID transactions.
    Furthermore, it implements the \textit{Medallion Architecture} (Bronze, Silver, and Gold tiers), preserving raw immutable ingestion data to ensure full reprocessing flexibility over time.

    \item \textbf{Machine Learning Layer:} This analytical module fulfills the primary objective of the research: real-time anomaly detection through advanced machine learning models consuming refined features from the data lakehouse.

    \item \textbf{Observability Layer:} Once operational metrics and diagnostic outputs are consolidated in the Gold layer, this tier presents actionable insights to operators through comprehensive visualization dashboards, enabling real-time monitoring of system health and robot anomalies.
\end{itemize}

\section{General Architectural Decisions}
\label{sec:arch_decisions}
\textit{Implementation: Chapter~\ref{chap:system_implementation}, Sections~\ref{sec:implementation_methodology} and~\ref{sec:containerized_deployment}.}

In addition to the component-specific design decisions presented in the following sections, several cross-cutting architectural principles were established to guide the development of the entire platform.

\subsection{Containerized Microservice Architecture}

The complete platform was designed following a containerized microservice approach.
Each functional layer of the architecture is deployed as an independent Docker container, including the source systems, messaging infrastructure, stream processing services, data storage components, and machine learning modules.

This modular design provides several advantages.
First, it promotes loose coupling between system components, allowing individual services to be developed, tested, and maintained independently.
Second, it simplifies system scalability, since each component can be replicated or upgraded without affecting the rest of the platform.
Finally, it increases the long-term maintainability of the solution, as individual modules may be replaced by alternative implementations provided that the communication interfaces remain unchanged.
Consequently, the architecture is centered on well-defined interfaces rather than on specific software implementations, facilitating future evolution of the platform.

\subsection{Interface-Oriented Design}

To maximize interoperability and future extensibility, communication between architectural layers is performed through standardized interfaces and message formats.
This design principle ensures that a component can be replaced without requiring major modifications in the remaining layers.
For example, the simulated AGV fleet used during development could be replaced by a real fleet management system, while preserving the same MQTT and VDA 5050 communication contracts.
As a result, the architecture remains independent of specific hardware vendors or software providers.

\subsection{Event-Driven Architecture}

An event-driven architecture was adopted as the communication paradigm for the entire platform.
Rather than relying on direct point-to-point interactions between services, all components communicate through an intermediate event streaming layer.
This approach significantly reduces coupling between producers and consumers, allowing individual services to evolve independently without affecting other parts of the system.
Additionally, new services can be integrated into the platform with minimal effort by subscribing to the existing event streams.
The event streaming layer acts as the system's central source of truth, providing a unified and consistent mechanism for distributing telemetry, operational events, and analytical results across the architecture.
This design improves scalability, extensibility, and maintainability while facilitating the integration of future data processing and monitoring capabilities.

\subsection{Separation of Training and Inference Pipelines}

The machine learning subsystem was designed following a clear separation between training and inference workloads.
Model training is performed offline using Python-based machine learning frameworks that consume historical data and engineered features stored in Apache Iceberg tables.
This approach provides flexibility for feature engineering, experimentation, hyperparameter tuning, and model evaluation.

In contrast, model inference is integrated directly into the Apache Spark streaming pipeline.
Once a model has been trained and validated, it is exported and embedded into the stream processing layer, allowing predictions to be generated in real time as new AGV telemetry events are processed.
This design avoids the latency associated with external prediction services and enables seamless integration with the event-driven architecture.

The separation of training and inference responsibilities allows each workload to be optimized independently.
Training processes prioritize model accuracy and experimentation capabilities, whereas inference processes prioritize low latency, scalability, and operational reliability.
Furthermore, the architecture facilitates future model updates, since newly trained models can be deployed to the streaming environment without requiring modifications to the surrounding data processing infrastructure.

\section{Source Systems Layer}
\label{sec:arch_source_systems}
\textit{Implementation: Chapter~\ref{chap:system_implementation}, Section~\ref{sec:source_system_simulation}.}

In designing the data ingestion pipeline, a preliminary study was conducted to determine the optimal source of truth for the system.
At first, the possibility of utilizing a physical Autonomous Mobile Robot (AMR) in real time was evaluated.
However, this approach was discarded for the training phase due to two primary constraints: first, only a single real unit was available, which is insufficient to represent a fleet-scale source system; second, the physical hardware lacked the specific internal telemetry sensors required for comprehensive anomaly detection analytics.

As a second approach, a search was conducted for publicly available industrial datasets containing multi-variable telemetry from AGVs and AMRs.
While several sources were identified, none provided the precise combination of electrical, mechanical, and thermal variables necessary for the anomaly detection module.

Given the limitations of both physical deployments and existing public datasets, the decision was made to implement a high-performance simulation framework capable of emulating an entire fleet of AGVs deterministically.
Since the chosen simulation environment, built upon the open-source repository \texttt{bekirbostanci/vda5050\_vehicle\_simulator} \cite{bostanciVda5050}, did not natively incorporate deep physical powertrain dynamics, it was adapted to model core electromechanical and thermal variables.
To ensure seamless integration with downstream data consumers, the messages published by the simulated robots strictly adhere to the \textbf{VDA 5050} \cite{vda5050standard} interoperability standard, extended to include custom telemetry payloads.

\section{MQTT Broker Layer}
\label{sec:arch_mqtt}
\textit{Implementation: Chapter~\ref{chap:system_implementation}, Section~\ref{sec:mqtt_broker_implementation}.}

The adoption of the VDA 5050 communication standard directly influenced the design of the messaging layer.
Since VDA 5050 defines MQTT as the underlying communication protocol between fleet management systems and AGVs, the incorporation of an MQTT broker became a fundamental architectural requirement.

The broker layer acts as an intermediary between telemetry producers and data consumers, enabling asynchronous communication and decoupling the different system components.
This approach allows producers and consumers to evolve independently while maintaining interoperability through standardized message exchanges.

Several MQTT broker implementations were evaluated during the architectural design phase.
Eclipse Mosquitto was ultimately selected due to its maturity, open-source licensing model, low resource consumption, Docker compatibility, and widespread adoption within Industrial Internet of Things (IIoT) environments.

Furthermore, the publish/subscribe communication model facilitates horizontal scalability and simplifies the integration of future services.
New consumers can subscribe to existing telemetry streams without requiring modifications to the source systems, making the architecture more extensible and maintainable.

\section{Event Streaming Layer}
\label{sec:arch_event_streaming}
\textit{Implementation: Chapter~\ref{chap:system_implementation}, Section~\ref{sec:event_stream_implementation}.}

To establish an enterprise-grade backbone for telemetry ingestion, storage, and analytics, the architecture incorporates a distributed event streaming platform.
While the MQTT layer excels at lightweight device-to-broker messaging, an append-only distributed log is essential to serve as the immutable single source of truth, handle high-throughput event replay, and decouple analytical consumers from edge producers.

\subsection{Kafka provider selection}

During the architectural design phase, distributed streaming technologies were evaluated.
Although Apache Kafka represents the industry benchmark, \textbf{Redpanda} was selected as the central event broker.
Redpanda provides complete protocol-level compatibility with the Apache Kafka API, allowing ecosystem tools—such as Apache Spark Structured Streaming and Kafka Connect—to operate seamlessly without modification or proprietary client adapters.

The decision to adopt Redpanda instead of traditional Apache Kafka is justified by several architectural advantages:
\begin{itemize}
    \item \textbf{Native Performance and Predictable Latency:} Redpanda is engineered in C++ utilizing the Seastar asynchronous framework with a thread-per-core architecture.
    This eliminates the Java Virtual Machine (JVM) runtime overhead and avoids Stop-the-World Garbage Collection (GC) pauses.

    \item \textbf{Architectural Simplicity and Self-Contained Topology:} Unlike traditional Kafka deployments requiring dedicated Apache ZooKeeper clusters or resource-intensive KRaft JVM controllers, Redpanda implements native Raft\cite{raftgithub} consensus embedded directly within the broker binary.
    This significantly reduces operational complexity, container footprint, and deployment startup times.

    \item \textbf{Resource Efficiency in Edge and Development Environments:} The lightweight footprint of Redpanda enables high throughput and reliable partitioned persistence while conserving host computing resources, making it exceptionally well-suited for containerized edge gateways and Proof-of-Concept (PoC) deployments.

    \item \textbf{Integrated Developer Tooling:} The platform bundles the \texttt{rpk} management utility and the Redpanda Console user interface out of the box, streamlining topic inspection, consumer-group monitoring, and partition offset observability without requiring external monitoring containers.
\end{itemize}

By leveraging Redpanda as the event streaming backbone, the platform ensures durable event persistence, horizontal scalability, ordered event processing, and seamless integration with the wider Kafka ecosystem.
These characteristics make it an appropriate foundation for the real-time data ingestion and analytics requirements of the proposed architecture.

A defining element of the topic design is the selection of a consistent partitioning key across the streaming backbone.
All telemetry topics use the composite key \texttt{manufacturer : serialNumber}, which in the VDA~5050 standard unambiguously identifies a single physical vehicle \cite{vda5050standard}.
This choice is motivated by two complementary architectural guarantees.
First, because a Kafka-compatible log preserves ordering only \emph{within} a partition, routing every message of a given AGV to a fixed partition ensures strict chronological ordering of its state transitions, a prerequisite for correct kinematic reconstruction and windowed feature computation downstream.
Second, prefixing the serial number with the manufacturer prevents hash collisions between distinct vehicles that could otherwise share an identical serial number.
At the same time, different vehicles are hashed to different partitions, allowing analytical consumers such as Apache Spark to process distinct AGVs in parallel.
The key is therefore applied uniformly across the ingestion, feature, and inference topics so that the per-asset ordering guarantee is preserved end to end across the Bronze, Silver, and Gold tiers.

\subsection{MQTT to Event Streaming Ingestion Layer}

An architectural decision was required to establish the data bridge between the edge messaging layer (Eclipse Mosquitto) and the central event streaming bus (Redpanda), ensuring that vehicle telemetry producers remain decoupled from Kafka-specific protocols.

During the design phase, deploying a dedicated Apache Kafka Connect MQTT Source connector was evaluated.
However, the MQTT ingestion boundary only requires protocol adaptation between MQTT and Kafka-compatible event streams, without the need for advanced connector lifecycle management, schema evolution, or stream transformations.
Consequently, introducing a full Kafka Connect framework at this stage was considered architecturally unnecessary.
Instead, Telegraf was selected as a dedicated telemetry ingestion agent because it provides native MQTT consumer and Kafka producer capabilities, enabling direct protocol bridging while preserving the original telemetry payloads.
This approach minimizes architectural complexity, reduces the number of operational dependencies, and keeps the ingestion boundary focused exclusively on message transport responsibilities.

\subsection{Streaming to Time-Series Persistence: Decoupled Kafka Connect for QuestDB}

For real-time operational monitoring and visualization in Grafana, events must be streamed continuously into \textbf{QuestDB}.
Instead of relying on bespoke consumers or embedding message-bus client logic into the storage layer, the industry-standard \textbf{Apache Kafka Connect} framework was adopted in sink mode (\texttt{io.questdb.kafka.QuestDBSinkConnector}).

An architectural evaluation was conducted to determine how to interface the central event streaming bus (Redpanda) with the analytical engine (\textbf{Apache Spark}) for downstream anomaly detection workloads.

\section{Stream \& Processing Layer: Apache Spark}
\label{sec:spark-stream-processing}
\textit{Implementation: Chapter~\ref{chap:system_implementation}, Section~\ref{sec:spark-implementation}.}

In defining the computational backbone for telemetry transformation, analytical feature engineering, and scalable inference, an architectural decision was made regarding the stream processing engine.
\textbf{Apache Spark}, utilizing its \textbf{Structured Streaming} framework, was selected as the central engine for this layer.

In accordance with the scope of this chapter, this section outlines the architectural design decisions, component responsibilities, and data contracts that govern the stream processing tier, whereas the implementation is addressed in (Chapter~\ref{chap:system_implementation}).

While distributed event logs like Redpanda provide durable message buffering, they lack high-level compute primitives for complex multi-stage data processing and distributed machine learning inference.
Apache Spark was selected based on the following architectural design principles:

\begin{itemize}
    \item \textbf{End-to-End Horizontal Scalability:} Telemetry volumes scale proportionally with the number of operational AGVs.
    Decoupling stream processing into a distributed engine ensures that computational bottlenecks are eliminated at the architectural level, allowing processing capacity to scale across partitions without altering application logic.

    \item \textbf{First-Class Lakehouse Integration:} Selecting an engine with native support for open table formats (\textbf{Apache Iceberg}) ensures transactional consistency (ACID guarantees), snapshot isolation, and seamless interoperability with the S3-compatible storage layer without requiring external data ingestion services.

    \item \textbf{Adoption of a Dual-Sink Streaming Pattern:} Rather than coupling stream processing to a single egress target, it was decided to adopt a dual-sink architectural pattern across processing stages.
    Under this design decision, Spark concurrently commits processed records to historical Iceberg tables for long-term analytics while republishing the transformed events back into dedicated Redpanda topics for low-latency downstream consumption.
\end{itemize}

From an architectural perspective, the trade-off between continuous, single-event streaming (as offered by engines such as Apache Flink or Kafka Streams) and the micro-batch execution model was evaluated.
While single-event engines achieve marginally lower nominal latencies, the micro-batch approach was selected because the sub-second latency provided by Spark Structured Streaming fully satisfies the temporal requirements of AGV telemetry (sampling between 1~Hz and 10~Hz).
Furthermore, micro-batching significantly simplifies transaction coordination, commit atomicity, and file compaction when interfacing with lakehouse table formats, offering a more balanced architectural trade-off for this platform.

\subsection{Medallion Processing Pipeline and Job Topology}

To avoid monolithic processing architectures and enforce strict separation of concerns across data maturity levels, the stream processing tier is decomposed into three decoupled streaming stages following the \textbf{Medallion Architecture} pattern (Bronze, Silver, and Gold tiers).
Each stage is architecturally designed around distinct operational contracts, input/output interfaces, and analytical responsibilities:

\begin{enumerate}
    \item \textbf{Job 1: VDA5050 State Writer (Raw to Bronze Persistence)} The telemetry generated by AGVs constitutes a continuous stream of operational data. While this stream is suitable for real-time communication between system components, it cannot be considered a reliable long-term source for analytics, auditing, or machine learning workloads. Messages stored only in Kafka are inherently transient and depend on retention policies, making them unsuitable as the primary source for historical analysis. Consequently, a persistent storage layer is required to preserve the complete history of vehicle telemetry. This historical repository enables offline data exploration, reproducible machine learning experiments, anomaly investigations, and system traceability. Several architectural alternatives were considered during the design phase. One possibility consisted of storing only the latest state of each AGV. This approach was discarded because anomaly detection models require access to historical behaviour patterns rather than individual snapshots. Another alternative involved applying state-change deduplication during ingestion to reduce storage requirements. However, due to the continuous variation of sensor readings and the stochastic noise introduced by the simulator, consecutive messages rarely contain identical payloads. The storage savings obtained from deduplication would therefore be limited while introducing additional processing complexity. For these reasons, the Bronze layer was designed as an immutable repository containing all incoming VDA5050 telemetry messages without modifications, filtering operations, or feature extraction. The \texttt{vda5050-state-writer} job is responsible for materialising this architectural decision by persisting the complete telemetry stream from the \texttt{vda5050-state} topic into an Apache Iceberg table. The resulting dataset serves as the authoritative historical record of the system. \item \textbf{Job 2: Bronze to Silver (Feature Extraction and Kinematic Aggregations)} Although the Bronze layer preserves the original telemetry stream, the VDA5050 message format is primarily designed for interoperability between fleet management systems and AGVs rather than analytical processing. As a consequence, messages contain nested structures and arrays that introduce unnecessary complexity for querying, statistical analysis, and machine learning workflows. To decouple the operational representation of telemetry from analytical requirements, a dedicated Silver layer was introduced. The objective of this layer is to expose a clean, structured, and domain-oriented representation of the information that can be consumed consistently by data analytics and machine learning components. The transformations performed in this stage are described below. \paragraph{Flattening} The first design decision concerns the representation of telemetry data. Directly exposing nested VDA5050 messages to downstream consumers would require every analytical component to repeatedly navigate hierarchical structures. Such an approach would increase implementation complexity and reduce interoperability between processing modules. To address this issue, a flattening process converts the original hierarchical message into a tabular schema. This representation is more suitable for Apache Spark processing, Apache Iceberg storage, and future machine learning pipelines while preserving the semantic meaning of the original telemetry data. \paragraph{Feature Selection} A second design objective consists of identifying which information is genuinely relevant for anomaly detection. The original VDA5050 messages contain numerous operational fields related to order execution, navigation state, and protocol management. However, the anomaly detection use case considered in this work focuses on identifying abnormal physical behaviour of AGVs through their telemetry measurements. For this reason, the selected features prioritise vehicle kinematics, battery indicators, motor telemetry, and safety-related signals while excluding protocol-oriented information that does not contribute to the detection of physical anomalies. The selected Silver-layer schema is composed of the following attributes: \begin{itemize} \item \texttt{timestamp}: Event timestamp used for temporal ordering and sequence reconstruction. \item \texttt{manufacturer}: AGV manufacturer identifier. \item \texttt{agv\_id}: Unique AGV identifier. \item \texttt{map\_id}: Identifier of the operational environment. \item \texttt{pos\_x}, \texttt{pos\_y}: Vehicle position coordinates. \item \texttt{vx}, \texttt{vy}, \texttt{omega}: Linear and angular velocity components. \item \texttt{driving}: Vehicle motion state. \item \texttt{battery\_charge}: Remaining battery charge level. \item \texttt{battery\_health}: Battery health indicator. \item \texttt{battery\_voltage}: Battery voltage measurement. \item \texttt{battery\_current}: Battery current measurement. \item \texttt{battery\_temperature}: Battery temperature measurement. \item \texttt{charging}: Battery charging state. \item \texttt{motor\_current}: Motor current consumption. \item \texttt{motor\_voltage}: Motor voltage measurement. \item \texttt{motor\_temperature}: Motor temperature measurement. \item \texttt{motor\_speed\_rad\_s}: Motor rotational speed. \item \texttt{motor\_torque\_nm}: Motor torque. \item \texttt{motor\_power\_w}: Motor power consumption. \item \texttt{wheel\_slip}: Wheel slip ratio. \item \texttt{back\_emf\_v}: Back electromotive force voltage. \item \texttt{fault\_active}: Active fault indicator. \end{itemize} The resulting Silver-layer schema establishes a common analytical representation of AGV telemetry data. This dataset serves as the foundation for subsequent machine learning processes, providing a consistent and domain-oriented view of the physical state of the vehicles while remaining independent of the original VDA5050 message structure.

\section{Data Lakehouse Layer: Storage Architecture}
\label{sec:data-lakehouse-layer}
\textit{Implementation: Chapter~\ref{chap:system_implementation}, Section~\ref{sec:data-lakehouse-implementation}.}

To establish the analytical persistence foundation of the platform, the architecture incorporates the \textbf{Data Lakehouse} paradigm.
While the event streaming bus (Redpanda) provides transient message buffering and the time-series engine (QuestDB) serves real-time dashboards, an immutable, cost-effective storage tier is required to persist the multi-tier Medallion datasets (Bronze, Silver, and Gold), store streaming execution checkpoints, and serve historical telemetry for offline machine learning model training.

\subsection{Object Storage Provider Selection: MinIO}
\label{subsec:minio-provider-selection}

In modern data architectures, decoupling compute from storage is a fundamental design principle.
Rather than deploying traditional distributed file systems (such as Apache HDFS) that introduce heavy operational overhead and tight coupling between compute nodes and physical disks, the architecture adopts \textbf{Object Storage} as the core persistence medium.

During the architectural evaluation of object storage engines for on-premise, edge, and containerized deployment, \textbf{MinIO} was selected based on the following architectural criteria:

\begin{itemize}
    \item \textbf{Industry-Standard S3 API Compatibility:} MinIO provides complete protocol-level compatibility with the Amazon S3 REST API.
    This native compatibility allows upstream compute engines—specifically Apache Spark via its \texttt{hadoop-aws} S3A connector—and modern table management engines (Apache Iceberg) to interface with the storage tier using standard S3 client libraries without requiring proprietary adapters.

    \item \textbf{Hybrid and Edge Deployment Portability:} In industrial cyber-physical environments, telemetry architectures frequently run on local edge infrastructure or on-premise factory servers before synchronizing with corporate data centers.
    MinIO enables a cloud-native S3 storage layer directly within containerized on-premise environments, ensuring that analytical pipelines can be migrated seamlessly to public cloud object stores (such as AWS S3 or Google Cloud Storage) simply by updating connection endpoints, without modifying data access logic.

    \item \textbf{High-Throughput Columnar and Micro-Batch Workloads:} Written in Go, MinIO delivers lightweight resource consumption and high sequential read/write throughput.
    These characteristics are critical for handling the concurrent demands of Apache Spark's streaming checkpoints and continuous Parquet file ingestion.

    \item \textbf{Strong Consistency for Lakehouse Table Formats:} Modern lakehouse table formats, such as Apache Iceberg, rely on atomic commit guarantees and strong read-after-write consistency to manage metadata snapshots and prevent race conditions during concurrent write operations.
    MinIO provides immediate consistency for all object operations out of the box, fulfilling this foundational requirement.
\end{itemize}

\subsection{Table Format Selection: Apache Iceberg}
\label{subsec:table-format-iceberg}

Object storage engines such as MinIO provide durable byte-level persistence, but relying directly on raw columnar files (for example, bare Apache Parquet) introduces significant limitations in a concurrent streaming environment.
In particular, raw files offer no transactional guarantees, suffer from the ``small files problem'' under continuous micro-batch appends, and can expose dirty or partial reads when an analytical query overlaps with an ongoing write.
To overcome these issues, modern Lakehouse architectures interpose an open \textbf{Table Format} layer between the object store and the compute engines, endowing the data lake with database-grade semantics \cite{apache_iceberg}.

The three leading open table formats---\textbf{Apache Hudi}, \textbf{Delta Lake}, and \textbf{Apache Iceberg}---were considered during the design phase.
\textbf{Apache Iceberg} was selected as the analytical table format of the platform on the basis of the following architectural drivers \cite{okolnychyi2024iceberg}:

\begin{itemize}
    \item \textbf{Engine-Agnostic, Vendor-Neutral Specification:} Unlike Delta Lake, which has historically been closely associated with the Spark and Databricks ecosystem, Iceberg was designed from its inception as an open, engine-neutral specification.
    This enables the write path to rely on Spark Structured Streaming while leaving the read path free to use distributed SQL engines, DuckDB, or pure Python tooling (for example, \texttt{pyiceberg}) for offline machine learning, without runtime lock-in.

    \item \textbf{ACID Transactions and Snapshot Isolation:} Iceberg provides serializable isolation through an optimistic concurrency model built on atomic metadata commits.
    This guarantees that continuous micro-batch ingestion performed by Spark never interferes with the long-running, read-heavy scans issued by offline model-training routines, as readers always observe a consistent table snapshot.

    \item \textbf{Fit for Append-Only Telemetry Workloads:} While Apache Hudi is heavily optimized for Change Data Capture scenarios with frequent record-level updates and deletes, cyber-physical AGV telemetry is strictly append-only.
    Iceberg offers a leaner metadata layout better suited to high-throughput sequential appends and automated file compaction, without the record-indexing overhead that Hudi introduces.

    \item \textbf{Safe Schema Evolution:} As robotic platforms evolve, their telemetry payloads may add new diagnostic fields or retire obsolete ones.
    Iceberg supports column addition, renaming, and reordering as a purely metadata-level operation, preserving backward compatibility without rewriting historical Parquet files.
\end{itemize}

\subsection{Automated Lakehouse Maintenance Architecture}
\label{subsec:arch-lakehouse-maintenance}
\textit{Implementation: Chapter~\ref{chap:system_implementation}, Section~\ref{subsec:lakehouse-maintenance-job}.}

While low-latency micro-batching (15~seconds for Bronze and 3~seconds for Silver) fulfills the near-real-time ingestion requirements of the platform, it inherently introduces the \textit{small files problem} as an architectural side effect. Over continuous 24/7 industrial operation, appending new Parquet data files every few seconds produces tens of thousands of fragmented objects and inflates the commit snapshot tree within object storage. Left unmitigated, this file fragmentation severely degrades the metadata listing speed, partition pruning efficiency, and sequential scanning throughput of downstream machine learning training workflows.

To prevent performance degradation without burdening the real-time ingestion path, the architecture incorporates an independent, decoupled \textbf{Lakehouse Maintenance Tier}. Rather than performing inline compaction during micro-batch execution---which would destabilize streaming latencies---maintenance is orchestrated as an auxiliary operational component operating outside the main Medallion data flow. Architecturally, the maintenance tier addresses three distinct optimization concerns:
\begin{enumerate}
    \item \textbf{Data File Compaction:} Merging thousands of small micro-batch Parquet files into standardized target-sized columnar blocks (64~MiB) to optimize sequential I/O and columnar compression ratios.
    \item \textbf{Manifest Optimization:} Re-indexing and defragmenting Iceberg manifest files and manifest lists to accelerate file pruning during query planning.
    \item \textbf{Snapshot and Metadata Expiration:} Purging historical snapshot metadata and unreferenced orphaned Parquet data files that have been superseded by compacted files, bounding storage growth and metadata parsing overhead.
\end{enumerate}
Crucially, the maintenance process is triggered on demand through automated metadata inspection rather than arbitrary execution schedules, optimizing compute resource utilization in resource-constrained edge deployments.

\subsection{Bifurcated Storage Architecture: Operational vs. Analytical Persistence}
\label{subsec:bifurcated-storage}

A core architectural decision of the proposed platform is the explicit decoupling between the \textbf{operational time-series store} (QuestDB) and the \textbf{analytical object store} (MinIO):

\begin{itemize}
    \item \textbf{Operational Path (QuestDB):} Optimized for low-latency ingest and high-frequency SQL aggregation across rolling time windows, dedicated to live operator visualization in Grafana.
    \item \textbf{Analytical Path (MinIO / Lakehouse):} Optimized for massive, append-only historical telemetry persistence in columnar Parquet format, multi-tier Medallion curation, and high-throughput batch scanning required for offline machine learning model training.
\end{itemize}

This bifurcated storage design isolates analytical queries and heavy machine learning workloads from live operational monitoring, ensuring that intensive model training scans do not degrade dashboard rendering performance or message ingestion throughput.
